# ratatui 0.30 upgrade (v0.18.0) — design

## Purpose

Move envision from ratatui 0.29 / crossterm 0.28 to ratatui 0.30.2 / crossterm 0.29, and leave 0.29 behind entirely.

The driver is security. On `main` (`76dedb2`), `cargo audit` reports three findings that only a ratatui upgrade can remove, because ratatui 0.29 is the only path to both crates (`cargo tree -i`):

| Crate | Advisory | Kind | Path |
|---|---|---|---|
| `lru` 0.12.5 | RUSTSEC-2026-0002 (`IterMut` violates Stacked Borrows) | unsound | ratatui 0.29 |
| `lru` 0.12.5 | RUSTSEC-2026-0253 (use-after-free in `LruCache::pop()` on panic) | unsound | ratatui 0.29 |
| `paste` 1.0.15 | RUSTSEC-2024-0436 | unmaintained | ratatui 0.29 |

A throwaway probe resolved ratatui 0.30.2 + crossterm 0.29, and the tree audits clean: `lru` 0.18.5, no `paste`. With PR 1's lockfile refresh also applied, `cargo audit --deny warnings` exits 0.

The upgrade also unblocks hyperlinks (#125). It supersedes #126 (support both 0.29 and 0.30 behind feature flags), which is closed rather than implemented. Dual support would mean keeping the unsound, unmaintained 0.29 tree alive.

The maintainer's stated goal for this work: **the library should be as free of security issues as possible.** That goal drives the choices below that go beyond a minimal bump: the exact version floor, the default-feature trim, the audit criteria, and the follow-up `cargo deny` gate.

### Review history

- **Design stage:** five personas reviewed the design before it was written — downstream app developer, custom-backend author, Rust API/semver reviewer, security/supply-chain reviewer, and CI/QA + MSRV packager.
- **Written-spec stage:** five personas reviewed this spec — plan implementer, adversarial downstream user, security, API/semver, CI/QA — plus a peer Claude session ("claudio").
- **Decisions:** the maintainer decided every contested point.
- Must-fix items from both rounds are folded in and attributed where they changed the design.

### `cargo deny` policy (PR 6) — fixed here because PR 3's criteria reference it

- **advisories:** deny, including unmaintained and unsound. No ignore list.
- **sources:** crates.io only.
- **bans / multiple-versions:** `deny`, with a short `skip` list (maintainer decision). Each entry:
  - is caused upstream and cannot be fixed in envision;
  - carries, in a comment beside it, a **link to the upstream issue or PR** tracking the duplicate and the **upstream version that removes it**;
  - is re-reviewed at every release.

  The link and version make a stale entry visible as "waiting on X, and X has shipped", rather than relying on the per-release review to notice. An entry without a link cannot be added; if no upstream issue exists, one is filed first (a public action, confirmed with the maintainer) (claudio).

  Known entry after PR 3: `hashbrown` 0.16 (via `kasuari`) vs 0.17 (via `lru` and `ratatui-core`). A fresh full update also shows `syn` 2/3 and `miniz_oxide` (via `arboard`); these are evaluated when PR 6 is written.

  PR 6 depends on PR 7 so the dev-only `itertools` duplicate is already gone (claudio).
- **Direct-minimal-versions job (CI, gating):** `cargo +nightly update -Zdirect-minimal-versions`, then build, test and `cargo audit`. The job pins a **dated nightly** (e.g. `nightly-YYYY-MM-DD`, bumped deliberately), so a nightly regression cannot turn `main` red (CI/QA reviewer).
  - **What it covers:** envision's *own* declared floors. It catches a dependency declared at a version too old to compile against, or one with an advisory — e.g. `tokio = "1"` admitting a vulnerable release.
  - **What it does not cover:** transitive floors. It minimizes only direct dependencies, so the `lru` 0.18.0/0.18.1 window (§ 8), reached through ratatui-core, still resolves to the newest `lru` (claudio).
- **Full minimal-versions check (pre-release audit, not CI):** `cargo +nightly update -Zminimal-versions`, then `cargo audit`. This walks transitive floors and reproduces the § 8 window.
  - It is usually red for reasons upstream of envision, so it is not a CI job. An allowed-to-fail job would be a permanently red check that trains everyone to ignore it.
  - Instead it is a named step in each pre-release audit. Every finding is recorded in the audit report with its upstream cause and tracking link, and checked against the previous release's list, so new transitive-floor exposure is noticed.

## PR 3 design

### 1. Dependencies

```toml
ratatui = { version = "0.30.2", default-features = false, features = ["crossterm_0_29", "underline-color", "layout-cache"] }
crossterm = { version = "0.29", features = ["event-stream"] }
```

`serialization` keeps enabling `ratatui/serde` as today.

**Why `0.30.2` and not `0.30`** (security reviewer). `"0.30"` admits 0.30.0, which fails on three counts:
- its ratatui-core 0.1.0 requires `lru ^0.16`, so a consumer pinned there still resolves an `lru` flagged by RUSTSEC-2026-0253;
- it lacks `CellDiffOption`, which § 4 depends on (`since = "0.30.1"`, `ratatui-core-0.1.2/src/buffer/cell.rs:68`);
- it declares `rust-version` 1.86.

The floor is what was tested.

**Why `crossterm_0_29` explicitly** (API reviewer):
- ratatui-crossterm selects the highest enabled `crossterm_0_xx` feature.
- envision also depends on crossterm directly (`src/app/runtime/terminal.rs` raw-mode and `execute!` calls).
- Naming the feature pins both to the same crossterm, so they cannot silently diverge.
- `crossterm_0_29` enables `crossterm`, which enables `std`, so neither needs listing (security reviewer).
- `underline-color` is also turned on by ratatui-crossterm's own defaults; listing it is harmless and documents the dependency.

**Why trim default features** (security reviewer; maintainer decision):
- ratatui's defaults are `all-widgets` (= `widget-calendar`), `crossterm`, `layout-cache`, `macros` and `underline-color`.
- envision uses neither ratatui's calendar widget (it has its own `Calendar` component) nor `ratatui-macros`.
- Dropping them removes **7 crates from the compiled graph on Linux/macOS (6 on Windows)**: `time`, `time-core`, `deranged`, `powerfmt`, `num-conv`, `num_threads` (unix-only) and `ratatui-macros`. None returns via another path under envision's full feature set.
- **`Cargo.lock` only loses `ratatui-macros`.** Optional dependencies are still locked, and `ratatui-widgets` lists `time`, so it stays in the lockfile.
- Consequently, `cargo audit` (lockfile-based) will still report a future `time` advisory. Anything that means "the compiled tree" uses a feature-aware tool (`cargo deny`, `cargo tree -e normal`).
- `underline-color` stays because `EnhancedCell` captures `underline_color` (`src/backend/cell/mod.rs:37`).

Consequences for consumers, documented in MIGRATION:
- `envision::ratatui` (§ 3) does not expose ratatui's calendar widget or macros.
- A consumer who wants them adds `ratatui` directly with `features = ["widget-calendar"]` / `["macros"]`. Their requirement must be **compatible with envision's** (`>= 0.30.2, < 0.31`), or they reintroduce the two-versions error that § 3 exists to prevent (claudio).
- A consumer already on `ratatui = { …, default-features = false }` who relied on envision enabling `widget-calendar` or `macros` gets a compile error, and must name those features explicitly (adversarial-user reviewer).
- Consumers on ratatui's defaults are unaffected: feature unification turns the features back on for the whole graph.
- The trim therefore only shrinks the tree for consumers who do not depend on ratatui directly with defaults.

**`unicode-width` unpinned** (adversarial-user reviewer). ratatui 0.29 pinned `unicode-width = "=0.2.0"`; 0.30 allows `>= 0.2.0`, so the lockfile moves to 0.2.2, and envision's own `unicode-width = "0.2"` moves with it.

Spot checks found identical widths for ZWJ sequences, VS16, flags and Hangul. Two divergences remain:
- newer Unicode code points will differ;
- ratatui 0.30's `cell_width` gives halfwidth katakana with a voiced sound mark (e.g. "ﾊﾟ") width 2, where `unicode-width` gives 1.

envision's own remaining width maths (`line_input` chunking) uses `unicode-width`, so it can disagree with ratatui's on such sequences; `EnhancedCell::symbol_width()` and § 5 switch to ratatui's width (§ 4c). This is documented in the CHANGELOG, not worked around.

### 2. Backend error model

ratatui 0.30's `Backend` trait gained `type Error: core::error::Error`, and every method returns `Result<_, Self::Error>` (`ratatui-core-0.1.2/src/backend.rs:162-331`). This is the probe's only source of compile breakage.

**Chosen model (all reviewers): honest error types.**

**`CaptureBackend::Error = core::convert::Infallible`.**
- `CaptureBackend` cannot fail. Upstream's `TestBackend` makes the same choice (`ratatui-core-0.1.2/src/backend/test.rs:250`).
- **This is a permanent commitment.** Changing an associated type is breaking, so giving `CaptureBackend` a real error type later would need a major release. It is correct for a buffer, and is recorded as settled (claudio).
- **PR 5 cannot reopen it.** PR 5 adds `scroll_region_up` / `scroll_region_down` (required `Backend` methods under ratatui's `scrolling-regions` feature) and fixes `append_lines` forwarding. For `CaptureBackend`, all three are in-memory grid operations — shifting rows within a region, appending rows — that have no failure mode, just like `draw`. They return `Ok(())` under `Infallible`. For `DualBackend` they forward to the primary and propagate `P::Error`, which needs no change to either error type.

**`DualBackend<P>::Error = P::Error`.**
- The capture half cannot fail, so every error is the primary's; no "which half failed" error type is needed.
- Calls forwarded to the capture half are written `let Ok(()) = self.capture.draw(..);`. This pattern is irrefutable since Rust 1.82 and was verified to compile cleanly on 1.88.
  - `?` there does not compile: generic `P::Error` has no `From<Infallible>`, and adding that bound would be needless.
  - No `unwrap` or `expect` (security reviewer).
- `DualBackend::with_auto_capture` and `DualBackendBuilder::build` (`src/adapter/dual/mod.rs:75`, `:268`) only call `primary.size()`. They therefore return `Result<Self, P::Error>` / `Result<DualBackend<P>, P::Error>` instead of `envision::error::Result`. This keeps `DualBackend` usable with any backend without an envision-specific bound (custom-backend author).

**`impl From<Infallible> for EnvisionError`.**
- Body: `match e {}`, so there is no panic path.
- Verified: no coherence conflict with the existing `From<io::Error>`. envision has no blanket `From<E: Error>` impl.

**Runtime bound: `EnvisionError: From<B::Error>`, as method-level `where` clauses.**
- **Spelling.** This is the form `?` uses; the `B::Error: Into<EnvisionError>` spelling would force `.map_err(Into::into)` at each site.
- **Placement — methods, not impl blocks** (implementer and API reviewers). `Runtime`'s methods live in one ~680-line `impl<A: App, B: Backend> Runtime<A, B>` block (`src/app/runtime/mod.rs:192-872`). That block also holds plain accessors — `terminal()` `:311`, `terminal_mut()` `:316`, `backend()` `:321`, `backend_mut()` `:326` — which must stay unbounded.
- **The eight methods that carry the bound** (traced from the two converting sites):
  - `RuntimeCore::render` — the `?` at `src/app/runtime_core/mod.rs:45`;
  - `Runtime::with_backend_state_and_config` — `Terminal::new(backend)?` at `src/app/runtime/mod.rs:211`;
  - `Runtime::render`;
  - `Runtime::tick`;
  - `Runtime::run`;
  - `Runtime::run_ticks`;
  - `RuntimeBuilder::build` (`src/app/runtime/builder.rs:398`);
  - `ConfiguredRuntimeBuilder::build` (`src/app/runtime/builder_configured.rs:78`).

  The plan confirms the list with the compiler.
- `terminal.rs` and `virtual_terminal.rs` are impls for concrete backends (crossterm / capture), so they already satisfy the bound and need no clause.
- **Struct definitions are untouched.** `Runtime` (`src/app/runtime/mod.rs:105`), `RuntimeBuilder` (`builder.rs:168`), `ConfiguredRuntimeBuilder` (`builder_configured.rs:27`) and `DualBackend` (`src/adapter/dual/mod.rs:43`) keep their existing `B: Backend` / `P: Backend` bounds and gain nothing.
- **Probe-verified** (API reviewer):
  - a downstream generic function over `Runtime<A, B>` needs the bound only if it calls a bounded method;
  - calling one without it fails with **E0277** ("the trait bound `EnvisionError: From<<B as Backend>::Error>` is not satisfied"). E0599 would appear only if the bound sat on the impl block, which this design rejects (implementer reviewer, verified on 1.88).
- **Io classification is preserved.** Crossterm's error is `io::Error` (`ratatui-crossterm-0.1.2/src/lib.rs:230`), so terminal I/O failures keep surfacing as `EnvisionError::Io` via the existing `From<io::Error>`, and code matching `EnvisionError::Io` keeps working.

**Rejected:**
- **Keep `io::Error` on `CaptureBackend` and box everything else into `Other`.**
  - Silently reclassifies crossterm I/O errors from `Io` to `Other`, with no compile error.
  - `CaptureBackend` would advertise failures it cannot produce.
- **A new `EnvisionError::Backend` variant.** A second breaking change, for no gain over the chosen model.
- **Bound `B::Error: Error + Send + Sync + 'static`, boxed, with a runtime downcast to `io::Error`** (the custom-backend author's alternative).
  - It works for foreign error types with no user code.
  - But it decides the variant at runtime and excludes non-`Send` errors.
  - The chosen bound is stricter, and **loosening a bound later is not breaking**, so starting strict keeps this option open.
  - **Orphan-rule cost of the chosen bound:** a consumer whose backend's error type is foreign to them cannot write `impl From<ThatError> for EnvisionError` (probe: E0117). They wrap it in a **local error newtype** — and a newtype backend only if the backend itself is third-party. MIGRATION documents both.
  - All four official ratatui backends (crossterm, termion, termwiz, termina) use `io::Error`, so none hits this.

**`#[non_exhaustive]` on `EnvisionError`** (`src/error.rs:46`; API reviewer; maintainer decision):
- v0.18.0 is already breaking, so this is the cheapest moment to add it.
- Afterwards, adding a variant is non-breaking — for example one that carries context, such as which operation (terminal creation vs draw) failed.
- Effect on consumers: an exhaustive external `match` needs a `_ =>` arm (E0004 otherwise).
- Enum-level `#[non_exhaustive]` does **not** stop consumers constructing the struct variants (`Render { .. }`, `Config { .. }`, `Subscription { .. }`); only a variant-level attribute would (probe-verified).
- envision's own internal matches are unaffected.

**`TestHarness`.** `src/harness/test_harness/mod.rs:57` and `:113` call `.expect` on what become `Result<_, Infallible>` values. They become `let Ok(..) = ..;`. `TestHarness::render` returns a `Result` that can no longer fail; its signature is re-examined in the plan against its callers, and is simplified only if that is not itself a needless break.

### 3. Re-exports (maintainer decision)

**`pub use ratatui;` at the crate root.**
- envision's public API already exposes ratatui types throughout:
  - `src/layout/mod.rs:47-49` (`Frame`, `Terminal`, layout types);
  - `src/style/mod.rs:21`;
  - `src/lib.rs:489-492`;
  - `TerminalRuntime` at `src/app/runtime/mod.rs:158`;
  - `EnhancedCell::from_ratatui_cell`;
  - the `Backend` bounds.
- The re-export lets consumers use exactly envision's ratatui, and through it `ratatui::crossterm` (ratatui re-exports crossterm under its `crossterm` feature, which `crossterm_0_29` enables).
- That avoids the two-versions failure mode — "expected `ratatui::Frame`, found `ratatui::Frame`" — which the README's current `cargo add envision` + bare `use ratatui::…` invites (`README.md:56-63`). The README snippet is updated to use the re-export.

**No separate `pub use crossterm;`** (API reviewer):
- envision's public API exposes no crossterm types; the conversions in `src/input/convert.rs` are `pub(crate)`, and `CrosstermBackend` is a ratatui type.
- `envision::ratatui::crossterm` is the one path. A second re-export would only be another route to the same crate.

**This is a permanent policy commitment, recorded as such** (claudio, adversarial-user reviewer):
- The re-export makes all of ratatui's surface part of envision's API, including anything ratatui adds later.
- From v0.18.0 on, **every ratatui 0.x bump is a breaking envision release**, and envision will never straddle two ratatui versions behind features. This was already effectively true, because ratatui types sit in envision's signatures; the re-export makes it explicit.
- It also means features enabled on `ratatui` anywhere in a consumer's graph — e.g. `scrolling-regions`, `unstable-*` — unify into envision's build. PR 5 therefore lands before release, and MIGRATION states which ratatui features envision supports (security reviewer).

**Other re-exports.**
- **`Backend` trait** re-exported from `envision::backend`. It appears in envision's public bounds and must be implemented by custom-backend authors, but is not exported today.
- **`HorizontalAlignment` and `VerticalAlignment`** join `Alignment` in `envision::layout`. In 0.30, `Alignment` is a type alias for `HorizontalAlignment` (`ratatui-core-0.1.2/src/layout/alignment.rs:8`).

### 4. `EnhancedCell` — `SerializableDiffOption`, legacy mapping, private fields

**Background.** ratatui 0.30.1 deprecated `Cell::skip: bool` in favour of `diff_option: CellDiffOption`, with variants `None`, `Skip`, `AlwaysUpdate` and `ForcedWidth(NonZeroU16)`. envision reads it at `src/backend/cell/mod.rs:84` into `EnhancedCell { pub skip: bool }` (`:43`).

**4a. The mirror type** (four of five design-stage personas; maintainer decision):

```rust
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq, Hash)]
#[cfg_attr(feature = "serialization", derive(serde::Serialize, serde::Deserialize))]
#[cfg_attr(feature = "serialization", serde(rename_all = "snake_case"))]
#[non_exhaustive]
pub enum SerializableDiffOption {
    #[default]
    None,
    Skip,
    AlwaysUpdate,
    ForcedWidth(NonZeroU16),
}
```

- **Name.** Follows the existing `SerializableColor` / `SerializableModifier` convention for serializable mirrors of ratatui types.
- **Location and exports.** It lives in `src/backend/cell/` beside `EnhancedCell`, and is exported everywhere `EnhancedCell` is: `src/lib.rs:190`, the prelude at `src/lib.rs:477`, and `src/backend/mod.rs:11`.
- **Wire format.** `#[serde(rename_all = "snake_case")]`, matching `SerializableColor`: `"none"`, `"skip"`, `"always_update"`, `{"forced_width": 2}`. Golden files make the format permanent, so it is fixed here (API reviewer).
- **Serde gating.** Serde derives and attributes sit behind `cfg(feature = "serialization")`, as for its siblings. The `No Default Features` CI job compiles and tests with no features at all.
- **Why `#[non_exhaustive]` when `SerializableColor` is not** (`cell/mod.rs:168`). ratatui's `CellDiffOption` has already grown variants, and hyperlinks (#125) will exercise them, so the mirror reserves room to follow without a breaking change. This deliberate difference is stated in the type's rustdoc.

**Mapping copies upstream's effective rule, not the naive one** (CI/QA reviewer):
- Upstream diffing treats a cell as skipped when `diff_option == Skip || (skip && diff_option == None)` (`ratatui-core-0.1.2/src/buffer/diff.rs:203-205`, `is_skip`), so the deprecated field is still honoured.
- The mirror is therefore `Skip` when upstream's `diff_option` is `Skip`, *or* when it is `None` and the deprecated `skip` is `true`; otherwise it is the upstream value.
- The deprecated field is read in exactly one function, under a scoped `#[allow(deprecated)]` with a comment pointing at `is_skip` — the same thing upstream does.
- Third-party widgets still calling `set_skip(true)` are then captured correctly.

**`ForcedWidth` is descriptive data only** (security reviewer):
- No envision code sizes an allocation, a loop, or output from a captured `ForcedWidth` value. § 5's wide-glyph handling uses it only to decide which existing in-bounds grid cells to blank, clamped to the row's remaining width.
- `NonZeroU16` makes serde reject a zero width, with no extra validation code.
- A test loads a snapshot whose cells carry `ForcedWidth(65535)` and checks that rendering it to text/ANSI and replaying it neither panics nor allocates in proportion to the width.

**4b. Legacy JSON is mapped on load, not dropped** (security, adversarial-user and API reviewers; maintainer decision):
- Without care, a v0.17 snapshot cell with `"skip": true` would deserialize with the unknown field ignored, becoming `diff_option: None` and silently losing information.
- Instead, `EnhancedCell` deserializes through a private wire representation, `#[serde(from = "EnhancedCellRepr")]` or equivalent, that accepts:
  - an optional legacy `skip: bool`, `#[serde(default)]`;
  - an optional `diff_option`, `#[serde(default)]`.
- The two are folded with the same effective rule as above: legacy `skip == true` and absent/`None` `diff_option` → `Skip`.
- Serialization writes `diff_option` only, with `skip_serializing_if = "SerializableDiffOption::is_none"`, and never writes `skip`.
- Results:
  - ordinary cells serialize with no diff-option field;
  - v0.17 files load without loss;
  - future variants do not churn golden files again.
- `src/backend/capture/tests.rs:606` is existing deserialization *input* containing `"skip":false`. It needs no change and becomes one of the legacy-input tests (implementer reviewer).

**4c. `EnhancedCell` fields become private, with accessors** (API reviewer; maintainer decision):
- v0.18.0 is the cheapest moment, and the `skip` field is being replaced anyway.
- Struct-literal construction is already impossible from outside, because `symbol` is private.
- After this change every field is private:

| Field | Getter | Setter (public) |
|---|---|---|
| `symbol` | `symbol() -> &str` (exists) | `set_symbol`, `set_char` (exist) |
| `fg` | `fg() -> SerializableColor` | via `set_style` (exists) |
| `bg` | `bg() -> SerializableColor` | via `set_style` (exists) |

The audit scorecard's symmetry rule does **not** check this — it scans only `src/component/` (`tools/audit/src/code_analysis.rs:48-49`) — so test 10 pins the accessor set instead (API reviewer).

- `src/backend/cell/mod.rs` is 460 lines, so the accessors fit without breaching the 1000-line cap.
- **`symbol_width()` switches to ratatui's width.** It currently returns `unicode-width`'s width (`src/backend/cell/mod.rs:105-107`), which would disagree with § 5's blanking, and with ratatui's diff, on symbols such as "ﾊﾟ". It now returns ratatui's width of the symbol, as a `usize`, so envision uses one width definition everywhere.
  - **One crate-internal helper computes it**, and § 5 uses the same helper for every width it needs. For a symbol that is a single ASCII control byte (e.g. `'\n'`, reachable through `set_char`/`set_symbol`) it returns 1 without calling ratatui. `CellWidth for str` reports exactly 1 for such bytes in release builds, but has a `debug_assert!` that panics on them in debug builds (`ratatui-core-0.1.2/src/buffer/cell_width.rs`, `impl CellWidth for str`). For every other symbol it calls `CellWidth::cell_width`.
  - **Result:** the value always equals ratatui's release-build width, and consumers' debug tests can never panic through envision (adversarial-user reviewer).
  - **Test:** a debug-build test exercises `'\n'`, `'\t'` and `'\x1b'` through both `symbol_width()` and `CaptureBackend::draw`. This changes behaviour only for the divergent symbols; it goes in the CHANGELOG with the `unicode-width` note, and test 10b covers "ﾊﾟ" (API reviewer).

### 5. `CaptureBackend` emulates terminal wide-glyph semantics

**The silent change** (adversarial-user reviewer; maintainer decision):
- ratatui 0.30 rewrote buffer diffing (`ratatui-core-0.1.2/src/buffer/diff.rs`, `BufferDiff::next`, lines ~92–193).
- 0.29's `Buffer::diff` kept an `invalidated` counter and re-emitted the cells following a wide glyph after it was replaced (`ratatui-0.29.0/src/buffer/buffer.rs:491-505`).
- 0.30 re-emits trailing cells only when:
  - the previous wide cell had a non-`Reset` background or a "visible on blank" modifier; or
  - the new cell is a VS16 emoji sequence.
- A real terminal does not need the re-emission: printing narrow text over a wide glyph clears the whole glyph.
- `CaptureBackend` does not. Its `draw` overwrites only the cells it is given (`src/backend/capture/mod.rs:539-543`).

**Concrete failure.** Column 1 shows `x`. The next frame draws `中` at column 0, and ratatui does not send column 1. The next frame draws `a` at column 0 with column 1 blank in both buffers, so ratatui does not send column 1 again. The capture now reads `ax`, while the screen shows `a `. `last_modified_frame`, which is serialized, is also wrong for such cells. No current test covers wide→narrow across frames; existing wide-character tests are single-frame component snapshots.

**Fix: `CaptureBackend::draw` applies terminal semantics**, so a capture matches the screen whatever ratatui chooses to re-send:
**Width source.** Every width in this section comes from the § 4c width helper — ratatui's own `CellWidth::cell_width` (`ratatui::buffer::CellWidth`, public; `ratatui-core-0.1.2/src/buffer/cell_width.rs:19`, `cell.rs:309-317`) — `ForcedWidth(n)` when set, otherwise ratatui's width of the symbol. For incoming cells it is called on the `ratatui::buffer::Cell` being drawn; for an existing owner it is computed from the stored symbol (`CellWidth for str`) and its `SerializableDiffOption`. It is **not** `unicode-width`: the two disagree on e.g. halfwidth katakana with a voiced sound mark ("ﾊﾟ", ratatui 2 vs `unicode-width` 1, § 1), and the emulation must agree with the diff that produced the cells (adversarial-user and API reviewers). No per-cell width is stored.

**Continuation cells.** A *continuation cell* is a column `x+1 .. x+w-1` covered by an owner at `x` with width `w > 1`. Its symbol is blank. Its **style is not assumed**: `Buffer::set_style(area, …)` (`ratatui-core-0.1.2/src/buffer/buffer.rs:405-412`) restyles continuation cells along with everything else, so inside a Block/Paragraph background, a List/Table highlight row, or an envision themed background they carry that style (adversarial-user reviewer).

A *blank write* is a cell whose symbol is `" "` or empty, **whatever its style or diff option**. "Blanking" a cell below means setting its symbol to `" "` and stamping the current frame, leaving its style unchanged.

1. **Writing an owner** (a cell whose width `w > 1`) at `(x, y)` sets the continuation cells `x+1 .. x+w-1` to **reset blanks** (`EnhancedCell::new()`), stamped with the current frame. The range is clamped to the row. This is exactly what ratatui's own buffer holds there: `Buffer::set_stringn` resets every cell a wide grapheme covers (`ratatui-core-0.1.2/src/buffer/buffer.rs:363-365`). So the capture agrees with the buffer — and with `TestBackend` — and single-frame captures are unchanged from v0.17 (CI/QA reviewer, verified). Copying the owner's style instead would diverge from ratatui's buffer and change existing ANSI/JSON captures of every styled wide glyph.
2. **A blank write into a continuation column leaves its owner intact**, and records the written cell's style on the continuation cell. This is the case ratatui 0.30 produces deliberately: for VS16 emoji it re-emits the trailing cells after the owner, in the same `draw` (`ratatui-core-0.1.2/src/buffer/diff.rs`, `TrailingState`), and the crossterm backend really prints them (`ratatui-crossterm-0.1.2/src/lib.rs:242-274`). Those cells carry whatever style the area has. Treating them as overwrites would erase every VS16 emoji in captures — e.g. `"ok"` → `"✔️"` would capture as two spaces — and a Reset-only definition would still erase them inside any styled area (adversarial-user reviewer, two rounds).
3. **A non-blank write into a continuation column** blanks that glyph's owning cell and the owner's other continuation cells, as terminals do when the right half of a wide character is overwritten. The blanked owner **keeps its style** — terminals differ here, and envision fixes one documented behaviour rather than imitating any one terminal. A test pins it (adversarial-user reviewer).
4. **Writing a narrow cell over an owner** blanks the owner's former continuation cells.

Draw order within one call does not matter for correctness: rule 2 makes a trailing blank a no-op, and rules 1, 3 and 4 each leave the row in the state a terminal would show.

The plan decides how continuation ownership is tracked (e.g. derived from the owning cell's width on demand, rather than stored state). It must keep `CaptureBackend`'s memory footprint unchanged, with no per-cell owner pointer, and `src/backend/capture/mod.rs` under 1000 lines (currently 710).

Tests, at two levels. **Unit tests on `CaptureBackend::draw`** feed hand-built partial cell lists — exactly what a diff would send — so they fail before the emulation exists on either ratatui version (implementer reviewer). **Multi-frame tests through `Terminal` + `CaptureBackend`** cover the end-to-end cases:
- CJK wide → narrow;
- narrow → wide;
- VS16 emoji wide → narrow;
- narrow → VS16 emoji where the old trailing column was **not** blank (e.g. `"ok"` → `"✔️"`) — the emoji survives (rule 2);
- the same VS16 case inside a styled-background Block and inside a highlighted List row — the emoji survives and the continuation cell carries the area's style in ANSI and JSON output;
- a themed wide CJK glyph — its continuation cell matches ratatui's buffer (a reset blank), so ANSI/JSON output is unchanged from v0.17;
- a width-divergent symbol ("ﾊﾟ") — blanking follows ratatui's width;
- overwriting the right half of a wide glyph;
- a wide glyph at the last column;
- `ForcedWidth`.

Each asserts `to_plain` / `row_content` against what a terminal shows, and `last_modified_frame` on blanked cells.

### 6. Snapshot changes — 14 tests, proven upstream

**Probe result:** 7450/7464 nextest tests and 2578/2578 doctests pass. The 14 failures are insta snapshots — 11 in `component::chart` (including `x_labels_tests`) and 3 in `component::canvas` — where braille dots move by about one sub-cell.

**Two upstream changes explain them** (CI/QA reviewer):
1. **Rounding.** Grid mapping changed from truncation (`ratatui-0.29.0/src/widgets/canvas.rs:402-403`, `as usize`) to rounding (`ratatui-widgets-0.3.2/src/canvas.rs:460-461`, `.round() as usize`).
2. **Line clipping.** In 0.29, a line with an out-of-bounds endpoint was dropped entirely. 0.30 clips it (Cohen–Sutherland, `ratatui-widgets-0.3.2/src/canvas/line.rs`) and draws the visible segment.

**Acceptance is by a sound check, not eyeballing** (CI/QA reviewer). A script kept in the scratchpad, with its output pasted into the impl PR, checks each of the 14 old/new pairs:
1. **Same dimensions** for the old and new grids.
2. **Non-plot cells byte-identical.** Every cell that is not braille-or-space in *either* version — axes, tick labels, borders, legends, titles — is identical.
3. **Changes stay in the plot area.** Every differing cell lies inside the chart's graph-area rectangle, derived from the component's layout for that test.
4. **Sub-pixel comparison.** Both grids are decoded into 2×4-per-cell sub-pixel bitmaps:
   - a diff labelled **rounding** must have a Hausdorff distance ≤ 1 sub-pixel between old and new dot sets;
   - a diff labelled **clipping** must have every old dot within 1 sub-pixel of a new dot. Extra new dots are listed and attributed by hand to a specific clipped segment in the test's data.

Each diff's label (rounding / clipping) is recorded in the impl PR description.

**Pin test.** An envision test pins upstream rounding directly:
- on a 2×2 braille `Context` over `[1.0, 2.0] × [0.0, 2.0]`, `(1.5, 1.0)` maps to grid `(2, 4)`;

### 8. Residual consumer risk — `lru` floor

Even with the `0.30.2` floor, ratatui-core 0.1.2 requires `lru = "0.18"`. That admits 0.18.0 and 0.18.1, which are still within RUSTSEC-2026-0253 (fixed in 0.18.2). The security reviewer reproduced a resolution to 0.18.0 with `-Zminimal-versions`.

**Exploitability through ratatui is nil, and the evidence is recorded.** ratatui-core calls only `get_or_insert`, `put` and `resize` on its layout cache (`ratatui-core-0.1.2/src/layout/layout.rs:317, 325, 755`), never `pop()` or `iter_mut()`. Its keys and values — `(Rect, Layout)` and `(Segments, Spacers)` / `Vec<Rect>` — are plain data whose `Drop` cannot panic. The advisory's panic-during-pop path is therefore unreachable through ratatui. `lru` is a non-optional ratatui-core dependency, so dropping `layout-cache` would not remove it either.

**Resolution (maintainer decision):**
- PR 8 asks ratatui-core to require `lru >= 0.18.2`. When a fixed ratatui ships, envision raises its ratatui floor to it.
- The CHANGELOG security note states both the residual version exposure and the unreachability evidence, and tells consumers to run `cargo update -p lru` (any normal resolution already picks 0.18.5).
- **Rejected:** an unused direct `lru` dependency, or `[patch]` guidance, purely to force a floor. A library cannot apply `[patch]` for its consumers, and an unused dependency is a hack.

## Testing strategy — tests first, with a precise definition of "failing first"

Every test in the plan is labelled with one of three kinds (implementer reviewer):

- **(A) assertion-fail on 0.29** — compiles before the bump and fails its assertion.
- **(C) compile-fail on 0.29** — cannot compile before the bump. The expected error code is recorded in the plan (e.g. E0220 for a missing associated type, E0308, E0412).
- **(K) characterization** — passes before and after the bump. It pins behaviour that must not change. It is not expected to fail first.

| # | Test | Kind |
|---|---|---|
| 1 | `<CaptureBackend as Backend>::Error` is `Infallible` (static assertion, in its own test file so its compile failure does not mask the rest of the lib test target before the bump) | C (E0220) |
| 2 | A crossterm-style `io::Error` raised through `Runtime` surfaces as `EnvisionError::Io` | K, then its test backend gains `type Error` at the bump |
| 3 | An injected draw error from a failing test backend reaches `render`/`tick` as the expected variant | K, as above |
| 4 | Foreign error type: a custom backend whose `Error` is a local newtype around a third-party error, used through `Runtime::builder` and wrapped in `DualBackend`, compiles and propagates (trybuild `pass` case) | C |
| 5 | Negative bound case: the same backend *without* the `From` impl fails to compile — a `compile_fail,E0277` doctest, not a trybuild `.stderr` | C → stays compile-fail |
| 6a | A generic function calling `Runtime::backend()` with only `B: Backend` compiles | K |
| 6b | The same function calling `render()` without the bound does not compile (`compile_fail,E0277` doctest) | A — on 0.29 there is no bound, so the code compiles and the doctest fails; added in step 2 and seen failing there |
| 7 | `DualBackend` constructors return the primary's error unchanged | C |
| 8 | `SerializableDiffOption`: each upstream variant maps across; deprecated `skip == true` with `diff_option == None` maps to `Skip` | C |
| 9 | JSON: round-trip of every variant; ordinary cells emit no diff-option field; legacy `"skip": false` and **`"skip": true`** both load correctly; `ForcedWidth(0)` rejected; `ForcedWidth(65535)` is safe (§ 4a) | C |
| 10 | `EnhancedCell` accessors return what `from_ratatui_cell` / `set_style` / `set_diff_option` stored | C for `diff_option`; the other accessors are written in step 1 on 0.29 |
| 10b | `symbol_width()` returns ratatui's width: "ﾊﾟ" is 2, and control bytes are 1 with no debug panic | A — on 0.29 "ﾊﾟ" is 1; added in step 2 (implementer reviewer) |

| 11b | Wide-glyph emulation, multi-frame through `Terminal` (§ 5) | A where 0.30's diff differs from 0.29's; K where 0.29 already passes |

| 13 | `EnvisionError` is `#[non_exhaustive]`: an exhaustive external match without `_` fails — `compile_fail,E0004` doctest | A (it compiles today, so the doctest fails) |

**Every `compile_fail` doctest has a passing twin.** CI runs no nightly, so on stable a `compile_fail` doctest passes on *any* compile error, a typo included. Each negative case is therefore paired with an otherwise-identical doctest that compiles once the missing piece is added: test 5 with the `From` impl, test 6b with the bound, test 13 with the `_ =>` arm. The twin proves the negative fails for the intended reason (CI/QA reviewer).

**C-kind tests live in their own integration-test files** (`tests/`), as test 1 already does. A test that cannot compile on 0.29 would otherwise take the whole lib test target down with it, and hide whether the A-kind tests (11a, 12) are failing for the right reason in step 2 (CI/QA reviewer). Tests that need crate-private access stay in the lib target and are written in step 3 alongside the code they exercise.

**Negative tests are `compile_fail,EXXXX` doctests, not trybuild `.stderr` files** (CI/QA reviewer). The E0277 "the following other types implement trait `From`" list, and E0004's "defined here" note, differ between 1.88 and stable, and grow with every `From` impl on `EnvisionError`. A `.stderr` file would break one of the two CI legs. Doctest error codes are matched only on nightly, and the tests still assert non-compilation on every toolchain. The positive foreign-error case uses trybuild `pass`, which has no stderr.
